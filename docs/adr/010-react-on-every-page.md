# React runs on every page again

ADR 009 took React out of the browser on most pages, and replaced what it did with one hand-written script listening on `document`. That was worth it while MUI and Emotion came with React. Without them, what a page saves by not running React is the runtime itself, 128 KB gzipped on a club page as built (React DOM, Next's page runtime and the page's own code), which is mostly cached after the first page, and the time spent hydrating a club's tables. Against that, the site kept two ways of doing everything: React state on the Locked Season and CSV pages, and the script's DOM code everywhere else, with a contract of `data-` attributes between the package's markup and the site's script that only the site's tests checked. And the player dialog, which a Locked Season needed, couldn't be used for this season's players at all.

Decisions, so they are not "fixed" later:

- **Every page runs React** except the 404 page, whose only job is an inline redirect (ADR 009; the redirect moved to `proxy.ts` in [ADR 017](017-player-season-paths.md)). There is no `unstable_runtimeJS: false` and no history-reload script, since the router handles back and forward.
- **The components own their behaviour.** A table sorts on its header buttons, the club directory filters as it is typed in, and Export Report writes the report and downloads it when pressed. The sorting, filtering and report text are the data package's (`sortPlayers`, `buildReport`), as for the MUI package. Filters are React state too, so a count or a URL can follow them: the club report's status filter and the unreported games' filters. ADR 009 made the status filter CSS (`:has()`), but with React on every page that was a second way to filter, with rows marked up for the stylesheet to match. What CSS does well stays CSS: the optional columns (`<details>`), the jumps between sides and the skip link (anchors).
- **One player dialog, in every season, opened by the URL** (superseded by [ADR 017](017-player-season-paths.md): a player's detail is a page of its own, `/player/<cms-id>/<season-slug>/`). A name in a club report is a link to the report's URL with the player in it: `/club/<club-key>/?player=<cms-id>`, or `&player=<cms-id>` on a Locked Season's. The page reads the parameter and the dialog shows the player's verdict on each of the club's sides, from the club's record already on the page. Nothing else holds which player is open, so Back closes the dialog, a link to one can be shared, and the component keeps no state for it. The site's link component makes these same-page links shallow, with no fetch and no scroll. A query parameter rather than a nested path, because a nested path would need a static page per club and player, about 9,600 of them, each a whole club report. In this season the dialog also links to the player's own page, which is still built for every player (ADR 008). A CSV report's players still have no detail: their rounds are in the file the visitor uploaded.
- **The cost is accepted.** A club page now carries its record as page data for hydration (1.5–5 KB gzipped for most clubs, plus its share of the fixtures) and hydrates its tables. If a large club's page is measured to be slow on a phone, render its tables on demand rather than going back to a separate script.
