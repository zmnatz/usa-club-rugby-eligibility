# Player pages are generated on first request

**Supersedes "Player pages are static pages again" in [ADR 008](008-static-player-pages.md) for when a page is made (each player still has their own page with the verdict in its HTML), "Locked Seasons get no index file" in [ADR 013](013-published-player-index.md), and "A deployed build is always complete" in [ADR 012](012-netlify-next-runtime.md).**

Issue #85. Every build generated about 19,800 player pages, one per CMS id in the current season or any Locked Season. With club pages generated on request (ADR 014), they were nearly all of the build's work, and the reason the build needed a quick, partial form.

Decisions, so they are not "fixed" later:

- **The build generates no player pages.** `getStaticPaths` in `pages/player/[player]/index.tsx` returns no paths with `fallback: 'blocking'`. The first request for `/player/<cms-id>/` runs `getStaticProps` in the route's function and returns the full page, verdicts, season tabs and match tables in the HTML, so ADR 008's reason for a page per player still holds. No `revalidate`: as for club pages, the data only changes with a deploy and Netlify's cache is per deploy.
- **An id in no player index is a 404.** That covers mistyped ids and Name Withheld players, who are in no index. Next caches the 404 for the deploy.
- **Each Locked Season publishes its player index too**, as `seasons/<slug>.players.json`, the same `PublishedPlayersFile` shape as `players.json`, worked out by `lockedSeasonPlayerIndex` and checked by `verify`. Working a Locked Season's index out from its file means reading about 8 MB and calculating every club in it; for four seasons that was about 4.6 s on a cold lookup, against under a second for the current season with `players.json`. A cold player lookup now reads `index.json`, `fixtures.json`, `players.json`, `seasons.json` and each season's player index, then only the club files and Locked Season files that name the player. Data published without these files still works: the client falls back to working the index out. Additive to the published layout, so a new minor version.
- **The player route's function carries the Locked Season files.** Unlike the club route (ADR 014), a player page shows a tab for each past season, so `next.config.ts` lists `seasons.json` and `seasons/**` in its `outputFileTracingIncludes` with the current season's files. They are about 32 MB, well inside a function's limit. Route keys there are globs, so the brackets of `[player]` are escaped. (Since [ADR 019](019-faster-builds.md), no function carries `public/data`; it reads the files from the CDN.)
- **No build scoping.** With no club or player page built, `BUILD_CLUBS`, `build:quick`, `src/utils/buildScope.ts` and the screenshot job's `build-clubs.ts` are gone. Every build is complete, so the PR screenshot job builds the site as Netlify does and can capture any page; `{player}` in `test/playwright/config/screenshots.yml` takes a player from the published `players.json` instead of the prerendered routes.
- **`listPlayerIds` is gone with it.** `published.pastPlayerIds()` stays in the package, now read from the season indexes.
