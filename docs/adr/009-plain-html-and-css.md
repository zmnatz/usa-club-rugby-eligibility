# The site's screens are plain HTML and CSS, with one small script

The site used MUI and Emotion, through the component package. Every page carried MUI's runtime, Emotion's, React's hydration of a table of hundreds of cells, and a theme's worth of CSS variables, to show text, links and tables from data that is fixed at build time. The site is static, so this cost every visitor on every page for nothing they could see.

Decisions, so they are not "fixed" later:

- **The site has its own plain components; the package stays on MUI for now.** The screens are in `src/eligibility/`, a plain HTML version of the component package's screens. The package (`@zmnatz/usa-club-rugby-components`, ADR 005) is unchanged and still React and MUI, because the package is published on its own schedule, not in step with the site's deploys, so a breaking rewrite of it can't land with the site's change. A plain HTML release of the package can come later, from `src/eligibility/`. Until then, `src/eligibility/` keeps the package's rules: no Next.js imports, `@/` aliases, environment variables or route strings (`boundaries.test.ts`), so it can be moved back.
- **Semantic HTML and one stylesheet.** `src/eligibility/styles.css` holds every style, as `ec-` classes on `--ec-*` custom properties, with a dark scheme under `prefers-color-scheme`. It sets no page background, font or heading styles. The site's own chrome and prose are in `src/styles/site.css`, on the same variables.
- **CSS does what CSS can.** A club's sides are all on the page, with in-page links between them, rather than tabs. The status filter is radio buttons and `:has()`, the optional columns are checkboxes in a `<details>`, and the skip link is an anchor to a focusable row. None of these need a script. `:has()` is in every current browser; in one without it the filter and column choice do nothing and every row and column is shown, which is a safe failure.
- **One script, listening on `document`** (`src/eligibility/enhance.ts`, as `ENHANCEMENT_SCRIPT`, put in `_document`). It sorts a table by a column's `data-sort` values, filters the club directory, and downloads the export. It uses event delegation, so it covers markup React adds in the browser (the CSV report, a Locked Season's pages) as well as static HTML, and it can be included twice. Without it, every table is complete and in name order.
- **The export text is in the page.** `buildReport` runs when the page is rendered and its text goes in a `<template>`; the button downloads it. A club page needs no data and no React to export. The report is stamped with when the records were last updated, not the visitor's clock, so the page is the same every time it is built from the same data.
- **No player dialog.** A player's page already shows everything the dialog did, with more room. A row's name links to it, and a link works from the keyboard, middle-click and a shared URL without the code a modal needs. A Locked Season's and a CSV report's players have no page, so they show only the table, whose Reason column carries the verdict. The per-competition rounds grid the dialog showed for a CSV report is gone: those rounds are in the file the visitor uploaded.
- **No React in the browser where it isn't needed.** The home page, club pages, player pages, stats pages and the 404 page ship no Next runtime (`unstable_runtimeJS: false`), only inline scripts: this one, one that reloads on history navigation (`historyReload.ts`), and the 404 page's redirect of `/player/?id=` links, built from the tested `queryPlayerId` and `playerPath`. The Locked Season page and the CSV report still run React, because they load a file in the browser (ADR 006); they no longer carry MUI.
